# Dagoldol Phase 2 — Performance & Accessibility Audit

Baseline inspected: current `index.html`, current `style.css`, current `script.js`, plus the two files that the current HTML actually executes as part of the frontend experience: `pill-buttons.css` and `liquid-chrome.js`. The HTML explicitly loads those dependencies, so excluding them would make the performance/motion audit incomplete. fileciteturn25file1 fileciteturn25file0 fileciteturn24file1 fileciteturn24file0

This is a static-code audit. I do **not** have a Chrome Performance trace, Lighthouse result, layer tree, heap snapshot, GPU timeline, or a recording from a mid-range Android phone. I therefore do not claim measured FPS, INP, memory usage, or actual jank.

## Executive summary

- **Biggest performance risk:** the continuously animated full-viewport LiquidChrome WebGL canvas runs behind a stack of translucent `backdrop-filter` surfaces, including the sticky header and every product card. Static analysis strongly identifies this as the first GPU/compositing hotspot to profile.
- **Biggest accessibility barrier:** the size-selector radios are `display:none`; this removes the native radio controls from keyboard navigation/accessibility exposure while product selection is a required purchase step.
- **Second major accessibility issue:** the application has a custom focus trap, but its modals have no `role="dialog"`, `aria-modal`, programmatic labels, background inertness, or scroll lock; the separate image lightbox makes nested-modal behavior unsafe.
- **KEEP:** the existing skip link, explicit focus-visible styling, semantic labels on many main forms, lazy-loaded product images, bounded search/delivery debounces, Realtime channel teardown, and CSS reduced-motion rules.
- Source alone is sufficient to fix the size selector, modal semantics, admin tabs, focus visibility, contrast failures, eager admin loading, and several glass effects. Actual LiquidChrome GPU cost, memory behavior during large image uploads, and 721–1024 px rendering need browser/device profiling.

## Performance findings

### [PERFORMANCE] Reduce the WebGL + full-page glass compositing stack

**Evidence:** `index.html` contains fixed `#liquid-chrome-bg-shop`; `style.css` declares `.liquid-chrome-bg { position:fixed; inset:0; }`, `.shop-header` with strong `backdrop-filter`, `.product-card` with 20px backdrop blur, `.modal-panel` and `.login-card` with 24px backdrop blur. The loaded LiquidChrome module continuously renders its canvas. fileciteturn25file1 fileciteturn25file0

**Problem:** The canvas continuously changes pixels behind multiple transparent surfaces. This combination can increase GPU compositing and repaint work, particularly for the sticky header and multiple catalogue cards.

**Status:** Inferred performance hotspot from static code. Runtime severity needs verification.

**Why it matters:** A mid-range mobile GPU has to render the shader and then continually resolve translucent/blurred surfaces above it. Product cards multiply the affected surface count.

**Fix:** Preserve LiquidChrome as the primary visual effect, but remove blur from repeated elements:

```css id="0yite6"
.product-card{
  background:rgba(23,26,35,.90);
  backdrop-filter:none;
  -webkit-backdrop-filter:none;
}

.field input,
.field select,
.field textarea,
.promo-row input,
.chat-input-row input,
.filter-search-field,
.filter-bar select,
.header-filters select,
.payment-section,
.login-gate-message{
  backdrop-filter:none;
  -webkit-backdrop-filter:none;
}

.shop-header{
  background:rgba(14,16,22,.90);
  backdrop-filter:blur(8px) saturate(130%);
  -webkit-backdrop-filter:blur(8px) saturate(130%);
}
```

For `.login-card` and `.modal-panel`, reduce 24px to approximately 12–16px rather than eliminating the effect.

**Validation:** Chrome DevTools → Performance: record a 10-second scroll through catalogue on desktop and Android remote debugging. Rendering → Paint Flashing. Layers → inspect number/size of composited layers. Compare before/after GPU/main-thread activity. Lighthouse Performance may be recorded as supplementary evidence, but not as a substitute for the scroll trace. ([developer.chrome.com](https://developer.chrome.com/docs/devtools/rendering/performance?authuser=2))

**Impact:** High  
**Effort:** M  
**Risk:** Low  
**Depends on:** None  
**Regression risk:** Glass appearance becomes slightly more opaque; functionality does not change.

### [PERFORMANCE] Stop eagerly loading every hidden admin tab

**Evidence:** In `enterShop()`, the admin path executes a large `Promise.all()` containing `renderAdminOrders()`, `renderAdminProducts()`, `renderAdminBundles()`, `renderAdminBrands()`, `renderAdminFlashSales()`, `renderAdminPromos()`, `renderAdminMessages()`, `renderAdminActivity()`, `renderAdminAnalytics()`, and `renderAdminSettings()`, followed by `renderAdminAccounts()`. Clicking a tab later calls those render functions again. fileciteturn24file1

**Problem:** Hidden admin screens perform Supabase reads and DOM construction before the administrator requests them.

**Status:** Verified.

**Why it matters:** Initial admin entry does more network traffic, JSON parsing, array processing, SVG chart construction, image references and DOM replacement than is necessary to show the default Orders tab.

**Fix:** On admin entry, load only the visible tab plus cross-screen state genuinely needed by the header:

```js id="xr5xqe"
if (account.role === "admin") {
  shopScreen.classList.add("hidden");
  adminWelcomeName.textContent = currentUser;
  adminScreen.classList.remove("hidden");

  adminOrdersVisibleCount = ADMIN_ORDERS_PAGE_SIZE;
  await renderAdminOrders();

  initPresenceGeneric();
  subscribeDmRealtime();
  unreadChatCount = await computeMyDmUnreadCount();
  updateChatBadge();
  updateDocumentTitleUnread(unreadChatCount);
}
```

Keep the existing per-tab click handlers as the lazy loaders.

**Validation:** Chrome DevTools → Network: compare Supabase requests from admin login until Orders is usable. Performance → compare scripting and rendering time. Confirm each remaining tab loads correctly on first click and subsequent clicks.

**Impact:** High  
**Effort:** S  
**Risk:** Medium  
**Depends on:** None  
**Regression risk:** A hidden tab may currently populate shared caches that another tab accidentally relies on. Test Products → Bundles → Analytics → Accounts in sequence.

### [PERFORMANCE] Pause or bound the continuously animated LiquidChrome background

**Evidence:** `index.html` automatically initializes the LiquidChrome module for the body-level fixed background. The implementation continuously schedules rendering through `requestAnimationFrame()` and does not use the existing `prefers-reduced-motion` CSS policy to stop the WebGL animation. fileciteturn25file1

**Problem:** A decorative canvas continues consuming rendering resources even when the page itself is idle.

**Status:** Verified source behavior; actual device cost Needs verification.

**Why it matters:** Continuous animation consumes GPU/battery resources throughout browsing, checkout, chat and admin use.

**Fix:** At minimum:

1. Render a still frame when `prefers-reduced-motion: reduce` is active.
2. Pause rendering while `document.hidden`.
3. Either stop the decorative animation before five seconds or provide a Pause/Resume control.

Conceptually:

```js id="tyzf2l"
const reducedMotion = window.matchMedia("(prefers-reduced-motion: reduce)");
let running = !document.hidden && !reducedMotion.matches;

document.addEventListener("visibilitychange", () => {
  running = !document.hidden && !reducedMotion.matches;
  if (running) requestAnimationFrame(update);
});
```

A full implementation must ensure only one RAF chain can exist when visibility toggles.

**Validation:** Performance panel: idle 15 seconds before/after. Rendering panel: FPS/frame rendering activity. Android remote-debugging: compare while page is stationary. Verify no RAF work continues while the tab is hidden.

**Impact:** High  
**Effort:** S–M  
**Risk:** Medium  
**Depends on:** LiquidChrome source modification  
**Regression risk:** Background motion changes after tab switching or reduced-motion preference changes unless RAF lifecycle is carefully guarded.

### [PERFORMANCE] Avoid full catalogue DOM reconstruction for every catalogue interaction

**Evidence:** `renderCatalogueList()` runs:

```js id="z3fe70"
catalogue.innerHTML =
  visible.map((p, i) => buildFullProductCardHTML(p, i)).join("");
```

and immediately loops over `[data-action='cart']` and `[data-action='order']` to attach new handlers. Search invokes it after a 250ms debounce; filters, sorting and Load More invoke it directly. fileciteturn24file1

**Problem:** Every catalogue state change reparses and replaces all visible product cards.

**Status:** Verified.

**Why it matters:** At the initial 12 products this is bounded, but every Load More raises the reconstruction size. It also forces listener reattachment and discards DOM/focus state.

**Fix:** First remove per-render listener attachment and use one delegated listener:

```js id="lhx5lh"
catalogue.addEventListener("click", (event) => {
  const btn = event.target.closest("[data-action]");
  if (!btn || !catalogue.contains(btn)) return;

  const id = btn.dataset.id;
  const qtyInput = document.getElementById(`qty-${id}`);
  const qty = clampQty(qtyInput ? qtyInput.value : 1);

  if (btn.dataset.action === "cart") {
    openSizeModal(id, qty, "cart");
  } else if (btn.dataset.action === "order") {
    openSizeModal(id, qty, "order");
  }
});
```

Then remove the two `querySelectorAll(...).forEach(addEventListener)` blocks from `renderCatalogueList()`.

Do not introduce virtualization until profiling demonstrates a need.

**Validation:** DevTools Performance with 12, 24, 48 and 96 loaded cards. Measure scripting/DOM update duration while changing sort/filter. Confirm one click produces one action after many rerenders.

**Impact:** Medium  
**Effort:** S  
**Risk:** Low  
**Depends on:** None  
**Regression risk:** Incorrect delegation selector could affect recommendation cards if they use separate containers; keep their existing handlers unless deliberately migrated too.

### [PERFORMANCE] Prevent overlapping recommendation recomputation

**Evidence:** `loadRecommendationData()` reads non-cancelled orders, reconstructs product-line data, creates a co-occurrence map with nested product-pair loops, and computes trending quantities. `subscribeRecommendationsRealtime()` listens for order INSERT and UPDATE and calls `scheduleRecsRefresh()`. `refreshRecommendationsLive()` can reload data and rerender recommendations. fileciteturn24file1

**Problem:** The 30-second throttle is good, but there is no explicit in-flight refresh lock or visibility check.

**Status:** Inferred scaling risk. Current order volume is not available.

**Why it matters:** With larger order history or slow network, another scheduled refresh can overlap or do work while the application is backgrounded.

**Fix:**

```js id="dxyw4q"
let recsRefreshPromise = null;

async function refreshRecommendationsLive(){
  if (document.hidden) return;
  if (recsRefreshPromise) return recsRefreshPromise;

  recsLastRefreshAt = Date.now();

  recsRefreshPromise = (async () => {
    await loadRecommendationData();
    await renderTrendingSection();
    await renderRecommendedSection();
  })();

  try {
    await recsRefreshPromise;
  } finally {
    recsRefreshPromise = null;
  }
}
```

Keep the existing 30-second throttle.

**Validation:** Network panel with artificial Slow 3G; trigger several order changes. There should never be overlapping recommendation-order fetches. Performance panel should show one recomputation window.

**Impact:** Medium  
**Effort:** S  
**Risk:** Low  
**Depends on:** None  
**Regression risk:** A refresh arriving while hidden is skipped until another trigger unless a `visibilitychange` refresh is also scheduled.

### [PERFORMANCE] Move large image decode/resize away from the most memory-heavy path

**Evidence:** `resizeImageToBlob()` uses `FileReader.readAsDataURL()`, constructs an `Image`, allocates a canvas at resized dimensions, draws the decoded source and calls `canvas.toBlob()`. The helper is used before Storage uploads. fileciteturn24file1

**Problem:** A 12–50 MP camera image still has to be decoded before downscaling; the Data URL introduces additional memory overhead.

**Status:** Verified implementation; real memory pressure Needs verification.

**Why it matters:** On memory-constrained phones a large upload can generate a long main-thread task or transient memory spike.

**Fix:** Prefer `createImageBitmap(file)` where supported, then fall back to the existing implementation. Also reject unreasonably large dimensions/file sizes before decode.

Do not assign a numerical file-size threshold without a product requirement.

**Validation:** DevTools Memory + Performance. Upload representative 12 MP, 24 MP and largest permitted photos on Android. Inspect peak JS/graphics memory and long tasks.

**Impact:** Medium  
**Effort:** M  
**Risk:** Medium  
**Depends on:** Representative production image sizes  
**Regression risk:** Browser-specific image-format differences; retain a FileReader fallback.

### [PERFORMANCE] Add a deliberate 721–1024px tablet bridge

**Evidence:** `.hero` changes at `max-width:960px`, while the principal header/admin/modal reflow begins only at `max-width:720px`; later `600`, `480`, and `420` rules compound the cascade. fileciteturn25file0

**Problem:** Tablet widths can receive a compact hero with desktop-density header, filters and admin spacing. Multiple independent `480px` and `720px` blocks also make cascade behavior difficult to reason about.

**Status:** Verified breakpoint gap; actual visual breakage requires runtime verification.

**Why it matters:** Layout wrapping can increase page height, repaint area and accidental overflow; `overflow-x:hidden` can conceal it.

**Fix:** Add a narrowly scoped bridge rather than redesigning all breakpoints:

```css id="hsq6w0"
@media (min-width:721px) and (max-width:1024px){
  .shop-header{
    padding:16px 24px;
    align-items:flex-start;
  }

  .header-filters{
    order:3;
    flex:1 1 100%;
    min-width:0;
  }

  .admin-tabs{
    padding:0 24px;
  }

  .admin-panel{
    padding:28px 24px 64px;
  }
}
```

Then consolidate duplicate `max-width:480px` blocks only after visual regression testing.

**Validation:** Browser widths 721, 768, 820, 912, 960, 961 and 1024px. Check `document.documentElement.scrollWidth === document.documentElement.clientWidth`; temporarily remove `overflow-x:hidden` while testing to expose hidden overflow.

**Impact:** Medium  
**Effort:** S  
**Risk:** Low  
**Depends on:** Browser visual test  
**Regression risk:** Existing deliberate header wrapping may change.

### Glass surfaces

A reliable static ratio cannot be calculated for text rendered over:

```css id="eyv3ob"
background: rgba(..., .35);
backdrop-filter: blur(...);
```

when the composited background is a changing WebGL shader/gradient. The final background pixel varies by location and frame.

For those cases:

**Foreground:** typically `#FFFFFF`, `#D6DAE4` or `#A4ACBF`  
**Background:** translucent glass + animated canvas  
**Ratio:** N/A statically  
**Required:** 4.5:1 normal text  
**Status:** **NEEDS IN-BROWSER MEASUREMENT**

A deterministic fallback such as `#D6DAE4` on solid `#171A23` yields **12.42:1**.

## Accessibility findings

### [ACCESSIBILITY] Restore keyboard-accessible native size radios

**Evidence:** `renderSizeOptions()` creates genuine:

```html id="44vp3f"
<input type="radio" name="size-feet" ...>
```

but `style.css` then applies:

```css id="i04bml"
.size-option input{ display:none; }
```

After every `change`, `renderSizeOptions(product)` reconstructs the entire radio group. fileciteturn24file1 fileciteturn25file0

**Problem:** `display:none` removes the native radio controls from sequential keyboard navigation/accessibility exposure. The required product-variant selection is therefore not reliably keyboard operable.

**Status:** Verified.

**Why it matters:** A keyboard-only user can reach “Continue” without being able to navigate/change the product size using normal radio semantics.

**Fix:**

### [ACCESSIBILITY] Complete the modal system instead of relying only on a focus trap

**Problem:** The modal system has:

- Focus entry: **present**
- Tab trap: **present**
- Shift+Tab trap: **present**
- Escape: **present**
- Basic single-modal focus restoration: **present**
- Disabled controls excluded from trap: **present**
- Dialog role: **missing**
- `aria-modal`: **missing**
- Accessible programmatic title: **missing**
- Background inertness: **missing**
- Scroll locking: **missing**
- Nested-modal stack: **not supported safely**

**Status:** Verified.

**Why it matters:** Screen-reader users are not told they entered a dialog, may navigate into content behind it, and nested interactions can restore focus incorrectly.

**Fix:** For example:

```html id="88kvcm"
<div id="cart-modal" class="modal-overlay hidden">
  <div
    class="modal-panel"
    role="dialog"
    aria-modal="true"
    aria-labelledby="cart-modal-title"
    tabindex="-1">
    <button ...>×</button>
    <p class="eyebrow">Your Cart</p>
    <h2 class="modal-item-name" id="cart-modal-title">
      What you've added
    </h2>
    ...
  </div>
</div>
```

Do the equivalent for every modal with its own heading ID.

Replace the single:

```js id="kbmd5h"
let lastFocusedBeforeModal = null;
let activeModalEl = null;
```

with a stack of modal states so nested dialogs/lightboxes can restore the correct previous focus target.

Add:

```css id="eszxq5"
body.modal-open{
  overflow:hidden;
}
```

and apply `inert` to the active screen/background while a dialog is open.

**Validation:** WCAG **2.4.3 Focus Order**, **2.1.1 Keyboard**, **4.1.2 Name, Role, Value**. Test:

1. Open with keyboard.
2. Verify focus enters intended first control.
3. Tab through all controls.
4. Tab from last → first.
5. Shift+Tab first → last.
6. Press Escape.
7. Verify focus returns to opener.
8. Attempt screen-reader navigation outside modal — background must be unavailable.
9. Verify page cannot scroll behind modal.
10. Repeat while opening a nested lightbox.

([w3.org](https://www.w3.org/WAI/WCAG21/understanding/focus-order.html))

**Impact:** High  
**Effort:** M  
**Risk:** Medium  
**Depends on:** Lightbox fix below
