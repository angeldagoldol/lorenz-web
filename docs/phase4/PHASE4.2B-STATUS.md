# Dagoldol Phase 4.2B — Commerce Authority Compatibility Status

Date: 2026-08-20

## Purpose

Phase 4.2B closes the remaining direct browser inventory-mutation path without overwriting the newer Dagoldol 3.3.5 frontend.

The current browser performs checkout as separate operations: it calls `decrement_stock_for_order()`, inserts directly into `orders`, then attempts a separate promo `used_count` update; cancellation updates `orders.cancelled` and calls the restore RPC separately. The Phase 4.2B compatibility migration preserves those call shapes while removing their direct inventory authority.

## Resulting authority model

After the candidate migration:

- `decrement_stock_for_order(jsonb)` remains callable by authenticated users **only as a read-only availability validator**.
- `restore_stock_for_order(jsonb)` remains callable by authenticated users **as a no-op compatibility shim** so older clients cannot double-restore inventory.
- the actual stock mutator lives in the non-exposed `dagoldol_private` schema and is not executable by authenticated users;
- customer order INSERT remains owner-bound for Dagoldol 3.3.5 compatibility;
- the order trigger replaces browser product/bundle names and prices with live database values;
- active flash-sale price is recomputed from live rows;
- bulk fee is recomputed;
- promo eligibility and `used_count` are validated/consumed under row lock;
- stock is decremented under product-row locks in the same order INSERT transaction;
- cancellation restores stock in the same order UPDATE transaction;
- payment reference/proof namespace and payment amount fields become persisted/protected order fields;
- saved customer order fields other than legal cancellation/rating state remain immutable.

## Important Phase 4.3 boundary

This is **not** the final server-authoritative checkout required by Phase 4.3.

The current delivery fee is still generated by the browser's route/geocoding flow. Phase 4.2B validates that the quote is finite/non-negative and freezes it after INSERT; it deliberately does not introduce a new maximum that could reject legitimate long-distance route fees. The master Phase 4.3 specification requires delivery pricing, final total, idempotency, and concurrency to move behind one trusted checkout service boundary.

Therefore do not claim:

- full server-authoritative delivery pricing;
- full checkout idempotency;
- Phase 4.3 complete;
- final production commerce certification.

## Verified pre-migration evidence

On 2026-08-20, the live read-only preflight confirmed the production database still has the expected Phase 4.2A compatibility state: the five payment/order columns are absent, public decrement/restore helpers still mutate products and remain `SECURITY DEFINER`, the atomic private stock function is absent, and the temporary owned-order INSERT policy is present. This is the intentional red baseline that Phase 4.2B is designed to change.

The live project currently has no Supabase development branches, so the candidate migration has not been runtime-compiled in an isolated Supabase branch from this environment.

## Production deployment status

The migration in this package has **not** been applied by ChatGPT to production.

It is designed from the verified live schema and current source behavior. Runtime migration compilation and the behavior regression still require an isolated Supabase development/staging database before production use.
